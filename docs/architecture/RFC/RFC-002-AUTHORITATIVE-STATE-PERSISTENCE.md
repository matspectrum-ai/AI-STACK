# RFC-002 — Authoritative State Persistence

Status: DRAFT
Date: 2026-08-09
Depends on:
- `docs/architecture/ENGINEERING-GRAPH.md`
- `docs/contracts/ENGINEERING-GRAPH-CONTRACTS.md`
- `docs/architecture/ADR/ADR-002-CONTRACT-TEST-BOUNDARIES.md`

## 1. Problem

The pure Engineering Graph kernel can decide whether a transition is eligible, but it does not persist authoritative workflow progress.

AI-STACK cannot safely execute agent work until it can guarantee that:

- stale writers cannot overwrite newer state;
- a transition decision and the resulting state mutation commit atomically;
- retries are accounted for before retry work becomes active;
- failures are durably recorded before recovery/escalation advances;
- process interruption can resume from exactly the last committed authoritative state;
- repeated delivery of the same commit request is idempotent;
- partial or corrupted persistence fails closed;
- authoritative history remains auditable.

Without these properties, an OMP execution may complete while AI-STACK loses, duplicates, or contradicts the authoritative graph state.

## 2. Objective

Define a storage-independent authoritative state contract that supports deterministic, auditable, crash-safe graph execution.

The first implementation backend is intentionally undecided by this RFC.

## 3. Non-goals

RFC-002 does not define:

- OMP execution transport;
- artifact/evidence payload storage;
- cryptographic evidence verification;
- policy evaluation implementation;
- distributed consensus;
- multi-region replication;
- UI;
- a specific database engine.

## 4. Authority model

The persisted authority consists of two complementary forms:

1. an append-only authoritative journal of accepted state-changing operations;
2. a current run snapshot derived from committed authoritative history.

The journal is audit authority. A snapshot is an optimization and resume checkpoint, not a license to rewrite history.

```text
Pure Graph Kernel
      |
      | TransitionVerdict
      v
Orchestration/Application Layer
      |
      | CommitRequest(expected revision + operation id)
      v
AuthoritativeStateStore
      |
      +---- atomic append ----> Journal
      |
      +---- atomic update ----> Current Snapshot
```

## 5. State revision

Every authoritative graph run has a monotonically increasing integer revision.

Rules:

- run creation starts at revision `0`;
- every committed state-changing operation increments revision exactly once;
- rejected/conflicting operations do not increment revision;
- a commit request MUST declare `expected_revision`;
- commit succeeds only if `expected_revision` equals the current revision;
- compare-and-swap validation and state/journal write MUST occur in one atomic storage transaction.

This is optimistic concurrency control.

## 6. Operation identity and idempotency

Every state-changing request MUST have a stable `operation_id` generated by the caller before commit.

The store binds one operation ID to one canonical operation payload digest.

Rules:

- first valid use may commit;
- replay of the same operation ID with the same canonical digest MUST return the original committed result without a second mutation;
- replay of the same operation ID with a different digest MUST be rejected as an idempotency violation;
- idempotency evaluation MUST occur inside the same atomic boundary as commit.

This protects against process/network retries after an unknown commit outcome.

## 7. Atomic commit bundle

An authoritative commit is a single all-or-nothing bundle.

Minimum bundle contents:

- operation identity and canonical digest;
- run identity;
- graph ID/version;
- expected state revision;
- one authoritative operation record;
- next run snapshot;
- records that MUST precede newly activated work, when applicable.

Examples:

### Transition commit

```text
TransitionDecision
+ next GraphRunState
= one atomic commit
```

### Retry activation

```text
FailureRecord already durable
+ incremented retry counter
+ retry activation state
= one atomic commit
```

### Recovery activation

```text
FailureRecord
+ recovery transition/activation
= one atomic commit
```

No reader may observe only a subset of a committed bundle.

## 8. Journal

The authoritative journal is append-only per run.

Each committed journal entry MUST contain:

- `journal_sequence` monotonically increasing within the run;
- `run_id`;
- resulting `state_revision`;
- `operation_id`;
- operation kind;
- graph ID/version;
- immutable operation payload or immutable payload reference;
- canonical payload digest;
- commit timestamp supplied by the store clock boundary;

Journal entries MUST NOT be updated or deleted through the normal state-store interface.

Administrative retention/migration is outside v1.

## 9. Snapshot

The current snapshot MUST contain enough information to satisfy `GraphRunState` and identify the journal position/revision from which it derives.

Rules:

- snapshot revision MUST equal the latest committed state-changing journal revision;
- snapshot update and journal append MUST be atomic;
- a snapshot that cannot be validated against its metadata MUST fail closed;
- implementations MAY rebuild snapshots from journal history when possible.

## 10. Resume

`loadRun(run_id)` returns only committed authoritative state.

For identical durable history, repeated loads MUST produce equivalent authoritative state.

After process interruption:

- committed operations remain visible exactly once;
- uncommitted operations remain invisible;
- callers resume from the latest committed revision;
- no agent narrative/session state may be used as a substitute for persisted graph authority.

## 11. Failure ordering

A failure that participates in retry, recovery, or escalation decisions MUST be durably recorded before or atomically with the operation that advances from that failure.

The system MUST NOT activate retry/recovery first and persist the failure afterward.

## 12. Retry ordering

When an automatic retry is activated:

- retry eligibility is evaluated by the pure domain kernel;
- the new retry count is persisted in the same atomic commit that activates retry work;
- no worker may receive the retry work from authoritative state before the incremented counter is durable.

This prevents crash loops from resetting retry budgets.

## 13. Transition ordering

The application layer obtains a pure `TransitionVerdict` and, when eligible, constructs a persisted `TransitionDecision` with a stable transition ID.

A successful transition commit MUST atomically:

1. verify expected revision;
2. verify operation-id idempotency;
3. append the transition decision to authoritative history;
4. persist the destination state/snapshot;
5. increment revision exactly once;
6. return the committed revision.

A stale transition verdict MUST not be committed after state has advanced.

## 14. Corruption behavior

Unknown, malformed, or internally inconsistent authoritative persistence MUST fail closed.

Examples:

- snapshot revision does not match journal head;
- duplicate journal sequence;
- journal revision regression;
- graph ID/version mismatch within a run;
- invalid canonical digest binding;
- operation ID bound to conflicting payloads.

The storage boundary MUST return a typed corruption/integrity result. It MUST NOT silently repair authoritative state during normal load/commit operations.

## 15. Storage port

The application layer depends on an AI-STACK-owned storage port, not on a database SDK.

Conceptual interface:

```text
AuthoritativeStateStore
  createRun(...)
  loadRun(run_id)
  commit(...)
  readJournal(run_id, after_sequence?)
```

Concrete types are defined in the Phase 3 contracts before executable tests.

## 16. Transaction requirement

Any conforming backend MUST provide an atomic primitive sufficient to implement:

```text
check expected revision
+ check idempotency key
+ append journal entry
+ update current snapshot
= one indivisible commit
```

If a backend cannot provide this guarantee, it is not conforming.

## 17. Backend portability

The contract MUST permit at least:

- a local single-host durable backend;
- a future networked SQL backend.

Backend-specific locking, WAL, SQL schema, migrations, and connection management belong to adapters/ADRs, not the domain contract.

## 18. Acceptance criteria

RFC-002 is implementable when strict contracts can express and executable tests can prove:

- stale writer conflict;
- exactly-once effect under idempotent replay;
- conflicting replay rejection;
- atomic decision + snapshot commit;
- deterministic resume;
- no visibility of uncommitted writes;
- monotonic revisions and journal sequence;
- immutable journal through the public port;
- failure-before-recovery ordering;
- retry-count-before-activation ordering;
- corruption fail-closed behavior;
- graph ID/version consistency;
- concurrent writers produce at most one winner for one expected revision.

No persistence production adapter may be written before these tests exist and are observed RED.
